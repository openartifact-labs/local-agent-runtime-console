# 系统架构

项目采用本地优先的分层架构。Web、Local API、SQLite 和 Provider 适配器均运行在用户电脑上，默认不依赖外部服务。

```text
Desktop Shell
  |
  +-- React Web -- REST / SSE --> Local Fastify API --> SQLite
                                      |
                                      +-- Provider Registry
                                             |
                                             `-- CodexProvider
                                                    |
                                                    `-- codex app-server (stdio JSONL)
```

## 模块职责

| 模块 | 职责 | 约束 |
| --- | --- | --- |
| `apps/web` | 任务看板、运行详情、使用分析和用户交互 | 只依赖通用 API 契约，不解析 Codex 私有协议。 |
| `apps/api` | 本机 API、SSE、任务编排、状态同步和持久化 | 默认只监听 loopback，不提供公网服务。 |
| `packages/contracts` | Provider 无关的领域对象和接口 | 不出现 Provider 专有状态与字段。 |
| Provider 适配层 | 将外部 Runtime 映射为通用契约 | 当前只有 `CodexProvider`。 |
| SQLite repository | 保存查询模型、受管运行、事件与输出快照 | 数据库位于用户电脑，迁移必须可审计。 |
| Desktop Shell | 生命周期、窗口、数据目录和本地服务管理 | Electron，生产态使用随机回环端口并限制外部导航。 |

## 主要数据流

### 发现任务

1. Local API 周期性请求 Provider 的任务列表。
2. Provider 适配器转换任务标识、状态和关系。
3. repository 更新本机查询模型。
4. Web 通过 REST 获取完整列表，通过 SSE 接收变更提示。

同步失败时保留最近一次本机数据，并将 Provider 标记为断开或降级；不得因为一次失败删除全部历史任务。

### 发起受管运行

1. 用户在 Web 中确认目录、提示词和可选模型。
2. Local API 校验输入并调用 Provider。
3. Provider 返回任务与运行标识。
4. Local API 持久化运行并持续接收事件、输出和指标。
5. Web 通过 SSE 增量刷新，断线后通过 REST 重新获取完整详情。

### 使用分析

分析器只读取本机可访问的 Provider 记录和观测台数据。聚合结果描述本机观测范围，不代表账号跨设备使用量，也不参与官方计费。

## Provider 抽象

Provider 需要按能力声明支持的操作，例如任务发现、任务发起、中断、事件流和使用分析。调用方先检查 capability，再显示或调用对应功能，避免为未来 Provider 伪造统一能力。

新增 Provider 的基本流程：

1. 在通用契约中确认现有领域对象是否足够。
2. 在独立适配层实现协议与状态映射。
3. 增加连接、分页、断线、超时和不完整数据测试。
4. 在界面按 capability 渐进展示功能。

## 数据与安全边界

- Local API 仅监听 `127.0.0.1`，CORS 不是身份认证。
- SQLite 文件、备份和运行日志不得包含 Codex 登录凭据。
- 提示词、命令与输出属于用户本机数据，默认不发送到 GitHub、Gitee 或维护者服务。
- 数据目录必须使用操作系统标准应用数据目录，不写入安装目录或源码目录。
- 桌面封装应限制导航、外部链接、文件协议和进程调用能力。
